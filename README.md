# Chicago Airport Taxi Demand

Проект прогнозирует почасовое число поездок такси, начинающихся
в аэропортовых зонах ORD и MDW в Чикаго.

## Источники

- Chicago Taxi Trips — поездки такси и целевой показатель спроса.
- BTS On-Time Performance — расписание и сведения о выполнении рейсов.
- Календарные признаки — час, день недели, выходной, месяц и праздник.

O'Hare соответствует community area 76, Midway — community area 56.
Это приближённые аэропортовые зоны, а не точные границы стоянок у терминалов.

## Получение данных Taxi

Скрипт `collect_taxi_trips.py` загружает месячные данные Taxi.
Исходные файлы сохраняются в `input_store/taxi_trips`.
Журнал и манифест загрузки сохраняются в `run_history`.

Скрипт `prepare_taxi_demand.py` проверяет временные метки и аэропортовые зоны,
а затем агрегирует поездки по местному часу. Последний месяц выгрузки
исключается как потенциально неполный. Причина исключения записывается
в отчёт качества.

Точные дубликаты не удаляются: в сохранённой выгрузке нет идентификатора
поездки, поэтому несколько поездок могут иметь одинаковые округлённые
время и аэропортовую зону.

## Получение данных BTS

Скрипт `collect_bts_flights.py` находит доступные месячные ZIP-архивы
в официальном каталоге BTS, скачивает их и сохраняет в
`input_store/bts_archives`.

Из архивов извлекаются записи с аэропортом назначения ORD или MDW.
Отфильтрованные месячные файлы сохраняются в `input_store/bts_arrivals`.
Журнал и манифест загрузки находятся в `run_history`.

## Объединённая почасовая таблица

Скрипт `build_airport_hourly_panel.py` объединяет целевой показатель Taxi
с расписанием и сведениями BTS по аэропорту и местному часу.
В расчёт входят только месяцы, присутствующие в обоих источниках.

День планового прилёта определяется по дате операции, времени вылета,
времени прилёта и плановой длительности рейса. Неоднозначные записи
попадают в отчёт качества и не включаются в агрегаты.

## Подготовка признаков

Скрипт `prepare_forecast_features.py` создаёт таблицу для одношагового
почасового прогноза.

Используются:

- календарные признаки: час, день недели, месяц, день года, выходной
  и федеральный праздник США;
- история спроса: лаги 1, 24 и 168 часов, скользящие средние за 24
  и 168 часов;
- показатели авиапотока за тот же местный час тремя месяцами ранее:
  плановые и фактические прилёты, отмены, перенаправления и средняя задержка.

Трёхмесячный лаг выбран, чтобы BTS-признаки относились к периоду,
доступному к моменту прогноза. Значения рейсов из прогнозируемого часа
не используются.

Пропуски средней задержки сохраняются вместе с индикатором пропуска.
Заполнение выполняется внутри конвейера модели.

## Обучение и сравнение моделей

Скрипт `train_and_compare_models.py` сравнивает:

- сезонный наивный прогноз по значению 168 наблюдений назад;
- Ridge-регрессию;
- Random Forest;
- XGBoost;
- LightGBM;
- CatBoost.

Разбиение выполняется хронологически: первые 70% временных точек —
обучение, следующие 15% — валидация, последние 15% — тест.
Оба аэропорта используют одинаковые временные границы.

Для Ridge проверяются 6 значений регуляризации, для каждого ансамблевого
алгоритма — 8 конфигураций. Параметры выбираются по MAE на равномерно
распределённых суточных окнах валидации.

Оценка имитирует прогноз на 24 часа: лаги внутри окна используют
предыдущие прогнозы. Фактический спрос внутри прогнозируемого окна
не подставляется в признаки.

Основная метрика — MAE, средняя абсолютная ошибка в поездках за час.
Дополнительно сохраняются RMSE, WAPE и MASE.

Результаты запуска сохраняются в
`model_runs/<идентификатор_запуска>`:

- `validation_candidates.csv` — результаты настройки параметров;
- `model_comparison.csv` — метрики на полной валидации и тесте;
- `recursive_predictions.csv` — прогнозы и фактические значения;
- `run_metadata.json` — разбиение, признаки, параметры и версии библиотек;
- `*.joblib` — обученные бинарные модели, хранящиеся локально и исключённые
  из Git.

По результатам сравнения основной моделью выбрана LightGBM.

## Интерпретируемость

Скрипт `explain_model.py` создаёт отдельные отчёты интерпретации, не меняя UI.

Используются:

- встроенная важность LightGBM по gain;
- permutation importance;
- вклады TreeSHAP для глобальной важности и отдельных прогнозов;
- график зависимости вклада от значения выбранного признака;
- сравнение средней важности признаков между Train + Validation и Test.

Файлы сохраняются в
`model_runs/<идентификатор_запуска>/interpretability`.
Журнал находится в `run_history/model_explainability.log`.

## Интерфейс и мониторинг

`app.py` запускает интерфейс Streamlit с вкладками:

- «Прогноз» — выбор аэропорта, даты и часа, прогноз на 24 часа,
  фактический спрос и календарный ориентир;
- «Мониторинг» — недельные MAE и WAPE, сдвиг входных признаков PSI,
  сигнал о необходимости проверить качество;
- «Календарный профиль» — средний спрос по дням недели и часам.

Мониторинг использует сохранённый исторический тестовый период. Данные
Taxi и BTS в текущей версии заканчиваются августом 2026 года, поэтому
мониторинг не является онлайн-мониторингом.

Порог сигнала качества равен средней недельной MAE validation плюс
два стандартных отклонения по полным неделям. Сигнал о проверке модели
появляется при превышении порога две полные недели подряд. PSI выше 0,25
показывается как сигнал сдвига данных; один только сдвиг не запускает
переобучение.

Недельные показатели качества считаются по сохранённым рекурсивным
прогнозам. PSI сравнивает наблюдаемые строки признаков каждой недели Test
с Train + Validation. Эти две оценки используют разные представления
входных признаков и интерпретируются отдельно.

Журнал работы интерфейса сохраняется в
`run_history/app_monitoring.log`.

## Порядок запуска

Команды выполняются последовательно из корневой папки проекта.

### Сбор и подготовка данных

```powershell
python collect_taxi_trips.py
python prepare_taxi_demand.py
python collect_bts_flights.py
python build_airport_hourly_panel.py
python prepare_forecast_features.py
